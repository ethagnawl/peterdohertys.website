AWS Wut

Introduction

I recently completed a client project that involved moving a few collaborating applications, each using various pieces of the AWS ecosystem, from one AWS account (owned by my client) to another (owned by their client). This is presumably a pretty common workflow for companies building AWS cloud based applications on behalf of others, transferring ownership because of an acquisition or similar. Unfortunately, AWS does not make this process as easy as it could or should be.

I also ran into a number of usability issues which I wanted to document, in the unlikely event some AWS stakeholder comes across this post. Primarily, though, I wanted a record of some of the issues I ran into that I could refer back to or share with collaborators when undertaking similar tasks in the future.

There are undoubtedly mountains of complexity behind the scenes at AWS I know nothing about, but I still think the UI/UX could be made much, much better than it is. For many years, AWS was the de facto cloud service provider, but Google Cloud Platform, Azure, Digital Ocean and others have gained lots of ground in recent years and many of their UIs are significantly better than AWS’. Perhaps they were kicking the can on these issues (they are aware of some of them – more on this below) because they were the only game in town or because of vendor lock-in. There are also now a vast number of “infrastructure as code” solutions which (mostly) preclude users ever having to manually interact with cloud service provider UIs. Many of my criticisms will be moot points with regard to people using AWS via those solutions.

MISC

  • I regularly saw a big, bright, red error popover which said “Too many requests.” in the course of doing standard tasks. This error didn’t prevent me from doing anything because the account was being rate limited or anything, it just served to confuse me.

  • AWS service UIs are wildly different experiences. It seems like the various services are moving towards a common UI and I saw messaging indicating this during this project, but I still regularly ran into subtly different workflows which were annoying enough to take me out of my flow and think for an extra second, even if only to consider how it was different from what I was expecting. Here are some examples:
    • type “delete me” to delete ECS service
    • type “name” to confirm delete almost everywhere … except where you need to type “confirm”
    • Elasticsearch confirmation prompts require you to select a checkbox
    • Some services contain fake links or links whose clicks are hijacked by JavaScript and prevent you from doing things like opening the link target in a new tab/window. Elasticsearch was an especially egregious offender. For instance, it’s not possible to ctr-click a database name and open it in a different tab from the main dashboard screen.

HTTP Event Triggers

In order for Lambda functions to do anything useful, they need to be triggered. Functions can be invoked directly, via the web UI, the AWS CLI or various client libraries. There are also a vast number of actions originating from other AWS services which can be used to trigger function execution (S3, Alexa, SQS and pretty much every other AWS service) but, in my very unscientific opinion, the most common use case is invocation via HTTP. Google Cloud Platform acknowledges this and Cloud Functions come with an HTTP API out of the box. However, in order to achieve this using AWS Lambdas, you need to first stand up an API Gateway which proxies HTTP requests into Lambda executions. Granted, this isn’t terribly complicated, but API Gateway has its own issues (see below) and there are many ways an integration can go awry. There should be a one-click solution to this problem like there is for GCP Cloud Functions.

API Gateway

deploy api to all stages? example could be better; add more examples

I regularly found myself making changes to an API Gateway endpoint that did not require testing in every stage before deployment. (For instance, adding CORS.) Unfortunately, there is no way to deploy changes to every stage at once; you must manually click through and deploy changes to each stage. I think this is probably well intentioned, as it makes accidentally deploying premature changes to all stages impossible, but I could see a separate flow which adds a prompt forcing you to acknowledge that this is what you want to do.
